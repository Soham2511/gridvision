# GridVision — Anomaly Intelligence Assistant: Tool Registry, Agentic GraphRAG and Knowledge Base

I want to implement the complete Anomaly Intelligence Assistant inside a separate, modular directory:

`ai/anamoly/`

All AI assistant-related functionality must remain inside this directory, including web scraping, document ingestion, vector database, graph retrieval, LangGraph agents, tool registry, memory, evaluation and documentation.

The assistant must integrate with the existing GridVision Flask backend and React frontend through clean service/API interfaces.

## 1. Inspect Existing Tool Infrastructure

First inspect the complete parent project to determine whether a dedicated AI tool registry already exists.

Important distinction:

- `backend/app/models/registry.py` is the ML Model Registry.
- It is NOT an Agent Tool Registry.

Search for any existing agent/tool registration mechanism.

If a suitable tool registry exists, reuse and extend it.

If not, create:

`ai/anamoly/tools/registry.py`

Implement a centralized registry that supports:

- Tool name.
- Tool description.
- Input schema.
- Tool implementation/handler.
- Allowed personas and permissions.
- Whether the tool has side effects.
- Whether user confirmation is required.
- Tool execution logging.
- Error handling.
- Tool availability/status.

All LangGraph agents must access functions through this registry.

Do not allow unrestricted Python execution, arbitrary SQL, filesystem access or unregistered tool calls.

## 2. Knowledge Base Location

I will manually place my collected PDFs, technical manuals, standards and other reference documents inside:

`ai/anamoly/raw_knowledge_base/`

Treat this as the original source directory.

Do not delete, overwrite, modify or relocate original documents.

The system must automatically discover supported files inside this directory.

Support:

- PDF.
- TXT.
- Markdown.
- HTML.
- JSON.
- Other appropriate technical document formats.

## 3. Web Scraping

Integrate the previously provided Python knowledge scraper.

Keep all scraping functionality under:

`ai/anamoly/crawler/`

Support configurable authoritative domains and seed URLs, including energy.gov, ferc.gov, dps.ny.gov, nyc.gov and osha.gov.

Requirements:

- Domain allowlisting.
- Respect robots.txt and website restrictions.
- Rate limiting.
- PDF downloading.
- Relevant HTML page extraction.
- Duplicate detection using SHA-256.
- Source URL and publication metadata.
- Incremental scraping.

Allow downloaded documents to be stored under a separate subdirectory of `raw_knowledge_base/` without overwriting my manually supplied documents.

## 4. Document Ingestion and Vector Database

Implement an independent ingestion pipeline under:

`ai/anamoly/ingestion/`

Workflow:

Raw documents → Text extraction → Cleaning → Page-aware chunking → Metadata enrichment → Ollama embeddings → Persistent vector database.

Use Ollama with configurable Qwen3-Embedding.

Use Chroma or an existing compatible vector database.

Create separate modules for:

- Document loading.
- PDF extraction.
- Text cleaning.
- Chunking.
- Embedding generation.
- Vector indexing.
- Retrieval.
- Incremental ingestion.

Preserve page numbers, document titles, publisher, source URL, publication date and document ID.

Support updates, duplicate detection, re-indexing and source deletion.

Persist embeddings across application restarts.

Do not embed raw customer time-series datasets or large CSV files.

## 5. Agentic GraphRAG

Implement a hybrid architecture:

- Vector RAG for technical documents.
- Structured queries for saved GridVision analysis results.
- Graph retrieval for relationships between customers, anomalies, events, areas and documents.

Use LangGraph for agent orchestration.

Use a graph database only if necessary; do not create duplicate infrastructure unnecessarily.

`ai/anamoly/vector_store/storage/chroma/persistent_db/`

Requirements:

1. Use ChromaDB with persistent storage.
2. Use Ollama Qwen3-Embedding for document embeddings.
3. Save all generated embeddings, vectors, indexes and metadata in the specified directory.
4. Do not recreate or re-embed all documents every time the application starts.
5. Support incremental ingestion and duplicate detection.
6. Maintain document IDs, source URLs, page numbers, publisher, publication date and chunk metadata.
7. Support multiple collections or versioned collections when needed.
8. Keep vector database code separate from its persisted data.
9. Configure the storage path through `GRIDVISION_ANOMALY_VECTOR_DB_PATH`, with the above location as its default.
10. Preserve the database across application restarts and Docker container rebuilds using a persistent volume.
11. Add the vector database storage directory to `.gitignore`. Do not commit generated embeddings or database files.
12. Do not place vector database files inside `raw_knowledge_base/`, `reports/`, `models/` or the frontend.
13. Do not delete existing vector database collections during application startup or routine ingestion.
14. Document backup, restoration, re-indexing and database migration procedures.

Ensure that the Flask application, LangGraph agents and ingestion pipeline all use the same configured persistent database rather than creating separate vector database instances.

### 2019 Dataset Date Guardrail — Mandatory

The current GridVision anomaly prediction dataset contains hourly electricity data for **1 January 2019 through 31 December 2019 only**.

The chatbot and analysis tools must enforce this date range.

1. All anomaly-related historical queries must use the available 2019 dataset.
2. If a user asks about a date in 2019, check for an existing completed application run first.
3. If no suitable run exists, offer or execute a new analysis using the existing configuration defaults.
4. Each analysis run must cover 1–7 days maximum.
5. If a user asks about a date in 2020, 2025, 2026 or any other unavailable period, clearly explain that the anomaly dataset currently covers only 2019.
6. Never silently substitute an unavailable date with a date from 2019.
7. Never fabricate anomaly records for dates outside the dataset period.
8. If the user does not specify a date, do not automatically analyse the current date. Ask which date or period in 2019 they want to investigate.
9. For queries such as "What happened yesterday?" or "Show today's anomalies", explain that the available anomaly data is historical (2019) and ask for a supported date.
10. For date ranges partially outside 2019, explain the unsupported portion and ask whether the user wants to analyse only the overlapping 2019 period.
11. Apply this restriction to run lookup, new analysis execution, event retrieval, memory-based answers, exports and agent tools.
12. Keep the date boundaries configurable from the dataset metadata rather than hardcoding different date assumptions in multiple modules.

**The dataset date range is a hard validation boundary, not merely a chatbot recommendation. Enforce it in the backend analysis service as well as the LangGraph agent.**
