# Energy redistribution assistant architecture

## Scope and trust boundaries

The assistant lives in `ai/assistant/`. It reads generated
`ai/output/redistribution_plan_<date>.json` files and never reads the trained
model or source Parquet during a question. Simulation JSON is untrusted data:
the Python loader validates an allowlisted structure, timestamps, grid IDs,
balances, network edges, capacities, and sent/received/lost energy before
records are used. Extra JSON fields, including any text that resembles
instructions, are not sent to either model.

The assistant sends the user question and a bounded set of relevant,
Python-calculated summary records to the configured response model (local
Ollama by default). It never sends the complete plan JSON. Do not put
credentials, personal information, or other sensitive material in a question.
LLM-generated prose is qualitative only; Python appends all numeric facts,
timestamps, grid lists, and energy totals from validated records. CSV and
images are generated by Python and Matplotlib, never by an LLM.

The supply, network, edge capacities, transfer plan, and losses are synthetic
demonstration assumptions. They do not describe actual electricity
infrastructure or measured supply.

## Components and request flow

```text
User query (CLI)
  |
  v
assistant.py: handle_user_query
  |-- load short, private local chat history
  |-- providers.py: initialize_llm(query model)
  |     `-- local Ollama /api/tags verifies the configured model by default
  |-- assistant.py: interpret_user_query + deterministic query grounding
  |     `-- intent, grid scope, explicit time, follow-up, and artifact action
  |-- schemas.py: validate JSON-only QueryRequest and supported intents
  |-- data.py: load_simulation_json(forecast_date)
  |     `-- validate 24 hours, 53 grids, balances, edges, capacities, losses
  |-- data.py: retrieve_relevant_records
  |     `-- exact timestamps, selected grid balances, connected neighbors/flows
  |-- data.py: calculate_summary
  |     `-- deterministic totals and conservation check
  |-- data.py: calculate_demand_solution (only for deficit advice)
  |     `-- direct edges, remaining surplus, unused capacity, least-loss first
  |-- deterministic action router
  |     |-- response model only when text is requested
  |     |-- render.py: CSV only when requested (fixed Pandas columns)
  |     `-- render.py: image only when requested (JSON network coordinates)
  |-- append the selected request to a short local history
  `-- return explanation and local artifact paths
```

### Python module responsibilities

| Module | Responsibility |
| --- | --- |
| `schemas.py` | Strict Pydantic schema for interpreter output and allowed intents/formats. |
| `providers.py` | Provider interface, secure credential loading, active-model verification, HTTP/API errors, configurable provider and model IDs. |
| `data.py` | Available-plan discovery, JSON validation, period/grid filtering, transfers, summaries, and deterministic direct-neighbor demand suggestions. |
| `render.py` | Fixed-schema CSV and selected-network Matplotlib image outputs; demand suggestions are visually distinguished from plan transfers. |
| `assistant.py` | Query interpretation, validation, qualitative response generation, history, and end-to-end orchestration. |
| `__main__.py` | Interactive and one-shot command-line interface. |

## LLM roles and model configuration

Two separate provider clients are created:

* **Query interpreter:** local `qwen3:8b` by default; it returns a
  schema-constrained JSON request. Python grounds explicit timestamps, dates,
  grid IDs, and durations against the user's words and available plan metadata.
* **Response generator:** local `batiai/gemma4-e2b:q4` by default; it returns
  brief qualitative prose. It is not asked to calculate totals or create files.
  Python-generated facts follow that prose.

The default provider is local Ollama at `http://127.0.0.1:11434`. It verifies
configured models using the local `/api/tags` endpoint and sends prompts to
`/api/chat`. Ollama's native JSON schema constraint is used for both roles.
No API key is needed for local inference. Groq's current model documentation describes
active hosted model IDs and its OpenAI-compatible API documents support for
both GPT-OSS model families. The exact account-accessible model list can vary;
initialization verifies each configured ID against the authenticated `GET
https://api.groq.com/openai/v1/models` endpoint and fails clearly if an ID is
unavailable. The Groq-hosted models are eligible for Groq's developer/free
usage subject to the account's current limits and access; no usage allowance
or permanent availability is assumed. OpenRouter is also supported directly
through its OpenAI-compatible API at `https://openrouter.ai/api/v1`; it reads
`Key_vault/Openrouter/api.key` or `OPENROUTER_API_KEY` and checks configured
model IDs against the authenticated model list. Model access depends on the
OpenRouter account. A generic `openai-compatible` provider adapter can be
configured for a compatible API endpoint, model list, and credential. It uses
`ENERGY_LLM_BASE_URL` and `ENERGY_LLM_API_KEY`; HTTPS is required by default.
Check Groq's
[model list](https://console.groq.com/docs/models),
[rate limits](https://console.groq.com/docs/rate-limits), and
[OpenAI-compatible API documentation](https://console.groq.com/docs/openai)
for current terms.

Model IDs and endpoints are configurable without source edits:

```bash
export ENERGY_QUERY_MODEL="openai/gpt-oss-120b"
export ENERGY_RESPONSE_MODEL="openai/gpt-oss-20b"
export GROQ_BASE_URL="https://api.groq.com/openai/v1"
```

To select OpenRouter, use `--provider openrouter` and optionally set
`OPENROUTER_QUERY_MODEL` and `OPENROUTER_RESPONSE_MODEL` or pass model IDs on
the CLI. The current defaults match the configured Groq model IDs but must
still be available to the OpenRouter account.

For local Ollama, set `OLLAMA_QUERY_MODEL` and `OLLAMA_RESPONSE_MODEL` or pass
`--query-model` and `--response-model`. Models must appear in `ollama list`;
the assistant checks them against the local server. `OLLAMA_HOST` defaults to
the loopback address. Local HTTP is allowed only for loopback hosts; remote
Ollama endpoints must use HTTPS. The key at `Key_vault/ollama/api.key` (or
`OLLAMA_API_KEY`) is used only when a remote HTTPS host is explicitly
configured, never for local requests.

For another OpenAI-compatible endpoint, choose
`--provider openai-compatible` and configure:

```bash
export ENERGY_LLM_BASE_URL="https://your-provider.example/v1"
export ENERGY_LLM_API_KEY="..."
```

`initialize_llm(provider, model)` supports Ollama, Groq, OpenRouter, and
generic OpenAI-compatible APIs and rejects unknown providers instead of
pretending they work. The `LLMClient` protocol and adapter boundary keep
provider selection independent from request interpretation and retrieval.

HTTPS requests use Python's verified default TLS roots. For a trusted private
or corporate CA not present in the default roots, set
`ENERGY_ASSISTANT_CA_BUNDLE` to a PEM CA file; it is added to the default
roots. Certificate verification must not be disabled.

## Credential handling

The Groq key is read from `Key_vault/Groq/api.key` (or from the
`GROQ_API_KEY` environment variable). The OpenRouter key is read from
`Key_vault/Openrouter/api.key` or `OPENROUTER_API_KEY`. The Ollama key is read
only for a configured remote HTTPS Ollama endpoint; local Ollama does not use
or transmit it. Key files are never printed, added to prompts, stored in chat
history, or included in errors. HTTP requests require
HTTPS by default; a configurable base URL exists for compatible provider
implementations. Restrict local key-file permissions and do not commit it.

## Request schema and time semantics

Interpreter output is validated against `QueryRequest` with these primary
fields:

```json
{
  "intent": "plan",
  "forecast_date": "2018-09-25",
  "start_timestamp": "2018-09-25T00:00:00",
  "duration_hours": 3,
  "grid_ids": [],
  "output_formats": ["text", "csv", "image"],
  "needs_clarification": false,
  "clarification_question": null
}
```

Supported intents include redistribution plan, hourly summary, network/grid
surplus and deficit, transfers, losses, grid plan, grid comparison, hourly comparison,
unmet demand, full-day summary, technical deficit-reduction suggestions,
image/CSV generation, follow-ups, basic concept help, and artifact
regeneration. Python grounds explicit grid IDs, dates, and timestamps rather
than trusting model guesses. A grid-scoped summary includes only the selected
grid balances; its directly connected simulated neighbors and relevant transfer
endpoints are included only as connection context.

* All timestamps are taken from the loaded plan; nonexistent times are not
  rounded or fabricated.
* If a date is omitted and there is exactly one available plan, that date is
  unambiguous. With multiple plans the assistant asks the user to choose.
* "Next" intervals start at the first forecast timestamp, or at the first
  available timestamp after the previous successful request's selected window.
* A full-plan summary without a selected hour covers all actual intervals in
  that file.
* "What about Grid N?" carries the preceding date, hour, and duration forward
  while replacing the grid filter. "Make it simpler" retains the preceding
  request and routes to text only.
* Image/CSV-only requests do not initialize the response model and generate
  only the requested file. Regenerating a previous artifact reuses the saved
  date, start time, duration, and grid filter without shifting the period.
* An ambiguous or unavailable date/hour produces a clarification response and
  no fabricated output artifacts.

## Retrieval, balances, and output formats

Python loads only the selected date's JSON, verifies the exact 24 hourly
records and 53 grid IDs, and filters timestamps and grid IDs locally.
Transfer rows are retained when either transfer endpoint matches a requested
grid; both endpoint balance rows are then included so CSV columns can be
populated deterministically.

The loader checks every grid's kWh accounting and every transfer's
`sent = received + lost` identity, network membership, fixed loss, and hourly
edge capacity. It stops with an explicit data error if metadata or checks
fail.

The CSV schema is fixed:

```text
timestamp,from_grid,to_grid,energy_sent_kwh,energy_received_kwh,
energy_lost_kwh,loss_pct,source_remaining_surplus_kwh,
destination_remaining_deficit_kwh
```

The CSV is valid with headers even if the selected period has no transfers.
Grid-specific CSVs include only transfers touching the requested grid(s);
balance columns use the corresponding source and destination records.
The image is plotted from the simulation's own centroid coordinates and fixed
network: surplus nodes are green, deficit nodes red, and other relevant nodes
blue. Arrows point from source to destination and are annotated with actual
Python-filtered sent/received/lost values. Only nodes and existing connections
relevant to the selected period and requested grids are drawn.

For `demand_solution`, Python considers the target grid's currently unmet
demand, adjacent source grids' remaining synthetic surplus, and each existing
edge's remaining hourly capacity after plan transfers. Candidate edges are
ordered by configured loss percentage, then distance and grid ID; each source
and edge is consumed at most once per hour. Suggested sent, received, lost,
and residual unmet energy are calculated locally. Suggested arrows are dashed
orange and labeled separately from actual plan transfers. This is a
deterministic feasibility heuristic, not a global optimization, economic
benefit calculation, or real-world operating instruction.

## Short conversation history

The default history is `ai/data/assistant_history.json`. It keeps at most four
recent turns plus the last successful structured request and paths of generated
files, stores no API credentials or simulation contents, and is written with owner-only file
permissions where supported. This makes "regenerate the last image" work
across questions and CLI restarts. Use `--history <path>` to select a separate
history file.

Rotating event logs default to `ai/logs/assistant.log`, with a 2 MB size limit
and three backups. `--log-file`, `--log-level`, and
`ENERGY_ASSISTANT_LOG_LEVEL` configure logging. Logs include event metadata
and error types, not user questions, prompts, credentials, or simulation
values. Basic concept questions are answered from local fixed definitions and
do not require provider access.

## Running and testing

Install the assistant's optional visualization dependency from the workspace
root:

```bash
.venv/bin/python -m pip install -r ai/requirements.txt
```

Start the conversational prompt:

```bash
.venv/bin/python -m ai.assistant
```

Or ask one question:

```bash
.venv/bin/python -m ai.assistant \
  --query "Show the next 3 hours of redistribution for grid 64"
```

Set `--simulations-dir`, `--artifacts-dir`, and `--history` to select data and
local output destinations. Successful data requests write PNG and CSV files
under `ai/assistant/output/` by default. LLM/provider errors, invalid model
availability, and invalid simulation data are reported explicitly.

Run isolated tests without contacting Groq:

```bash
.venv/bin/python -m pytest ai/test -q
```
