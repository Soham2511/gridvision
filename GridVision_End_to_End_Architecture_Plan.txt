Project architecture, directory structure, engineering standards, and build sequence

====================================================================
1. PURPOSE AND CURRENT SCOPE
====================================================================

GridVision is a smart-energy analytics platform with three customer-facing dashboard experiences:

1. Residential — customer/household month-end electricity bill prediction.
2. Commercial — factory-level energy-demand prediction and related operational metrics.
3. Government — region-level demand prediction to support grid planning and energy redistribution.

CURRENT IMPLEMENTATION GOAL
Build a working, end-to-end Python application in which:
- Three existing trained model artifacts (currently available as .pkl files) are loaded by a backend.
- FastAPI exposes validated prediction endpoints for the three models.
- Streamlit provides three dashboards and calls the FastAPI endpoints.
- Inputs, outputs, errors, model versions, latency, and relevant data/model parameters are logged in structured form.
- The project has repeatable data engineering, model evaluation, tests, quality gates, documentation, and a release process.

This is the initial application/integration phase. Do not assume the existing pickle files are production-ready until their training features, preprocessing, dependencies, target definitions, and evaluation reports have been checked. The plan is to package preprocessing and the estimator together into one versioned pipeline artifact wherever feasible.

The attached demo dashboard image and the three whiteboard sketches are design references. Keep the original uploaded images unchanged as reference assets. Suggested repository locations:

Use the original image files as supplied; these names are suggested destination names, not claims that the files have already been copied or converted. The demo dashboard is a visual guide, not a source of validated model outputs. Any figures shown in the mockup are illustrative.

2. ARCHITECTURAL PRINCIPLES
====================================================================

A. Separation of concerns
- Streamlit: presentation, navigation, user input, charts, and API calls only.
- FastAPI: HTTP endpoints, request/response validation, authentication/authorization hooks if needed, and API error handling.
- Application/service layer: orchestrates prediction use cases.
- Model layer: loads model artifacts and performs inference.
- Data layer: raw data ingestion, validation, transformation, storage, and reporting.
- Core/domain layer: shared schemas, domain rules, calculations, and exceptions.
- Observability layer: structured logs, request IDs, timings, model versions, and health checks.

B. Object-oriented design
Use small classes with one clear responsibility. Prefer dependency injection over global model objects. Define interfaces/protocols where multiple implementations are likely. Avoid putting model logic directly inside FastAPI route functions or Streamlit pages.

C. Validation at boundaries
Use Pydantic models for API requests/responses and configuration. Use explicit data contracts (for example, Pandera or Pydantic-based validation) for ingestion and transformed datasets where appropriate. Validate:
- Required columns and data types
- Null/missing values and acceptable ranges
- Timestamp format, ordering, duplicates, and expected frequency where relevant
- Feature names/order expected by each model
- Finite numeric values and sensible business constraints
- Prediction response fields and units

D. Reproducibility
Pin dependencies, define configuration through environment variables, track data/model versions, and provide repeatable commands for data validation, tests, training/evaluation, and local startup.

E. Safe artifact handling
Only load trusted pickle files. Pickle/joblib artifacts can execute code when loaded; never load an artifact from an untrusted source. Record artifact checksum, creation date, model version, training data version, feature schema, and compatible package versions.

F. No unsupported performance claims
Do not claim a model is accurate simply because it returns a prediction or has a high training R². Each model needs a documented evaluation on an appropriate held-out dataset. Use time-based splits for time-series prediction; prevent leakage.

4. THE THREE MODEL CONTRACTS
====================================================================

MODEL A — RESIDENTIAL CUSTOMER-LEVEL BILL PREDICTION
Purpose:
Estimate the customer's end-of-month bill from actual consumption so far plus forecast consumption for the remainder of the billing cycle.

Reference product rule from the project documentation:
- Prototype tariff: flat ₹10 per kWh, unless configuration changes it.
- Collect the first seven days of readings before displaying the first prediction.
- Starting on Day 8, forecast remaining consumption and add actual consumption in the current billing cycle.
- Refresh the estimate daily.
- Label the output as an estimate, not a guaranteed utility bill.
- The dataset has been described as roughly four years of 15-minute interval kWh readings and approximately 370 customer/meter columns; confirm the actual schema, coverage, units, and customer/meter meaning before implementation.
- A 15-minute reading already represents interval energy in kWh. Sum intervals; do not multiply each interval reading by 0.25 again.

Core calculation, when applicable:
actual_kwh_so_far = sum(valid interval consumption in current billing cycle)
predicted_remaining_kwh = model prediction for remaining cycle
estimated_month_end_kwh = actual_kwh_so_far + predicted_remaining_kwh
estimated_bill_inr = estimated_month_end_kwh * configured_tariff

Suggested endpoint:
POST /api/v1/residential/predict

Suggested request fields (finalise from the existing model's actual feature schema):
- customer_id (or anonymised household ID)
- forecast_timestamp
- billing_cycle_start and billing_cycle_end
- actual_kwh_so_far
- validated recent/history features required by the model
- data coverage/quality metadata

Suggested response fields:
- customer_id
- predicted_remaining_kwh
- actual_kwh_so_far
- estimated_month_end_kwh
- estimated_month_end_bill_inr
- tariff_inr_per_kwh
- prediction_timestamp
- model_version
- data_quality/coverage status
- explanatory caveats

Residential dashboard should show:
- Estimated month-end bill
- Actual consumption so far
- Forecast consumption for the remaining period
- Current monthly usage and estimated monthly usage
- Historical versus forecast usage chart
- Last-updated time and data coverage
- Trend in estimates over time, if prediction snapshots are persisted
- Clear prototype-tariff disclaimer

MODEL B — COMMERCIAL FACTORY-LEVEL PREDICTION
Purpose:
Provide factory-level energy-demand predictions for commercial operations. The exact target, horizon, granularity, input columns, and units must be taken from the current model and training documentation, not guessed.

Suggested endpoint:
POST /api/v1/commercial/predict

Request/response schemas must explicitly define:
- factory/site identifier
- forecast timestamp and horizon, if applicable
- required model features and their units
- predicted demand/usage target and unit
- model version and data-quality status
- any validated peak-period or cost fields, only if supported by the model/business rules

Commercial dashboard may include:
- Actual versus predicted factory load/demand
- Forecast horizon and peak-period indicators, if supported
- Factory/site selector
- Key demand metrics
- Model/data status and update timestamp
- Cost or load-shifting estimates only after their formulas and required tariff inputs are explicitly defined and tested

MODEL C — GOVERNMENT REGION-LEVEL PREDICTION
Purpose:
Provide region-level demand predictions to support grid planning and energy redistribution. Confirm the actual model target and output semantics before designing calculations or presenting results as operational recommendations.

Suggested endpoint:
POST /api/v1/government/predict

Request/response schemas must explicitly define:
- region identifier
- forecast timestamp and horizon
- required model features and units
- predicted demand/consumption and unit
- model version and data-quality status
- redistribution recommendations only if a separate, defined and validated optimisation layer exists

Government dashboard may include:
- Region-wise demand metrics
- Map or region selector
- Historical versus forecast demand
- Regional comparison table
- Peak-demand indicators, if supported
- Data freshness, model version, and quality status
- Redistribution outputs only when backed by a defined algorithm, constraints, and validation

IMPORTANT: The three endpoints are prediction endpoints. A prediction model does not, by itself, implement redistribution optimisation, tariff calculation, anomaly detection, or business recommendations. Those require separate logic and tests.

5. PIPELINE PACKAGING — ONE PKL PER MODEL
====================================================================

Target design:
Each artifact should be a fitted scikit-learn Pipeline (or compatible pipeline object) containing all learned preprocessing and the estimator. Use ColumnTransformer for column-specific preprocessing when appropriate.

Illustrative pattern:
- numeric pipeline: imputation and scaling if required
- categorical pipeline: imputation and one-hot encoding or another appropriate encoder
- ColumnTransformer: applies transformations to declared feature columns
- final estimator: trained model
- optional custom transformers: only if they are serialisable, deterministic, and covered by tests

Package the preprocessing and estimator together so inference receives raw, schema-valid model inputs and applies the exact training transformations. Do not independently refit imputers/encoders in FastAPI or Streamlit.

Critical compatibility checks:
1. Inspect each current .pkl: object type, required feature names/order, preprocessing included, target, library versions, and expected input shape.
2. If the current .pkl contains only an estimator, recover the exact preprocessing used during training and rebuild/retrain the full pipeline from training data.
3. Do not fabricate missing preprocessing steps or assume that a model can accept arbitrary raw columns.
4. Use the same feature engineering implementation for training and inference. Where possible, implement it as a tested transformer in the pipeline.
5. Fit all learned transformations only on training data, inside the training pipeline, to prevent leakage.
6. Validate incoming feature names, types, ranges, null policy, and ordering before inference.
7. Save the full pipeline with a metadata manifest containing:
   - model name and semantic version
   - artifact filename and SHA-256 checksum
   - target definition and target units
   - ordered feature list/schema version
   - training data version/date range
   - train/validation/test split dates or identifiers
   - package/Python versions
   - evaluation metrics and baseline comparison
   - training timestamp and code revision
8. Load artifacts only from a controlled, configured path. Fail readiness checks if an artifact is missing or invalid.
9. Never silently fall back to a different model version after a loading failure.

6. DATA ENGINEERING — BRONZE / SILVER / GOLD
====================================================================

BRONZE LAYER — RAW/INGESTED
Purpose: preserve source data and ingestion traceability.
Steps:
- Ingest from existing files or an explicitly configured feed.
- Store source-faithful data without silently overwriting the original.
- Record ingestion timestamp, source filename/system, batch ID, row count, and checksum where practical.
- Keep schema/column names and source values intact; add ingestion metadata separately where possible.
- Store data in an appropriate format such as CSV/Parquet.
- Make ingestion repeatable and handle duplicate batch submissions safely.

SILVER LAYER — CLEANED/VALIDATED
Purpose: make data typed, standardised, deduplicated, and quality-flagged.
Steps:
- Parse timestamps and define timezone handling.
- Validate column names and data types.
- Check missingness, duplicate keys/timestamps, invalid numeric values, impossible values, and unexpected frequencies.
- For interval time series, inspect gaps, duplicates, zero readings, negative readings, and extreme spikes.
- Do not automatically treat zero as missing; it may represent genuine zero consumption.
- Do not automatically delete or impute anomalies without a documented rule.
- Add quality flags and retain lineage to source records.
- Write a quality report with counts, rates, examples, and decisions.
- Keep cleaning transformations deterministic and tested.

GOLD LAYER — BUSINESS-READY DATA
Purpose: create curated tables for reporting, model inputs, and evaluation.
Steps:
- Generate the aggregations and features required by each model.
- Create documented hourly/daily/monthly or regional/factory summaries where relevant.
- Ensure every feature was available at the forecast timestamp.
- Keep target definitions separate from input features.
- Prevent future data leakage in time-series features and historical aggregates.
- Store schema/version, source lineage, row counts, and quality results.
- Do not force all three use cases into one common table if their grains and schemas differ.

DATA REPORT FOR EVERY DATASET
Generate a report for every raw/bronze/silver/gold dataset, including:
- Dataset name, version, source, generation time, and owner/context
- File/table format, dimensions, date range, and data grain
- Column names, inferred/declared types, and units
- Missing count and percentage per column
- Duplicate count and key uniqueness
- Numeric summary statistics and categorical value counts
- Timestamp cadence, gaps, and timezone where relevant
- Invalid/out-of-range values and quality-rule results
- Target distribution for labelled training datasets
- Row counts before and after transformations
- Excluded/imputed records and reasons
- Data lineage and transformation version
- A machine-readable JSON report plus a human-readable HTML/Markdown report

The report must distinguish a warning from a hard failure. Thresholds should be configured and justified; do not invent universal acceptable thresholds before inspecting the data.

7. MODEL EVALUATION AND METRICS
====================================================================

Every model needs a repeatable evaluation script and a saved report. Report performance on a held-out dataset that was not used for fitting or model selection.

Regression metrics, where applicable:
- MAE: average absolute error in the target's units.
- RMSE: penalises larger errors more strongly.
- R²: comparison against a mean-target baseline; interpret with the other metrics.
- WAPE or carefully defined percentage error when meaningful; guard against zero/near-zero denominators.
- Bias/mean error: reveals systematic over- or under-prediction.
- Error breakdowns by date, horizon, customer/factory/region, and relevant operating segment.
- Baseline comparison: report whether the model beats a simple, credible baseline.

Residential-specific evaluation, following the product specification:
- MAE in kWh for estimated month-end consumption.
- MAE in rupees for the estimated bill under the configured tariff.
- RMSE.
- WAPE/percentage error with low-denominator handling.
- Error by forecast day, household, and month.
- Chronological train/validation/test split.
- Reproduce the product rule: no displayed prediction during the first seven days; prediction starts on Day 8.
- Prevent leakage from current-month future consumption.
- Where feasible, evaluate generalisation to households not represented in training.

Commercial-specific evaluation:
- Use the target's true units and forecast horizon.
- Report MAE/RMSE and R² if regression is appropriate.
- Break down error by factory, forecast horizon, and peak/non-peak period where supported.
- Compare with a baseline such as a recent-period or seasonal-naive forecast, where appropriate.

Government-specific evaluation:
- Use the target's true units and forecast horizon.
- Report MAE/RMSE and suitable percentage metrics.
- Break down error by region and horizon.
- If the product later includes redistribution, evaluate that optimisation separately against explicit constraints and operational objectives; predictive accuracy alone does not validate a redistribution decision.

Evaluation reports should include:
- Dataset/split identifier and time range
- Model/artifact version
- Metric definitions and values
- Baseline results
- Error plots/tables and segment analysis
- Known weaknesses and failure cases
- Acceptance decision and reviewer/date

Do not set arbitrary numeric acceptance thresholds before measuring baselines and understanding business impact. Establish thresholds after the first reproducible evaluation.

====================================================================
8. PYDANTIC VALIDATION AND API DESIGN
====================================================================

Use Pydantic schemas at API boundaries and typed settings for configuration. Prefer separate request and response models for each use case.

For each endpoint:
1. Validate request structure, required fields, types, identifiers, timestamps, units, and constraints.
2. Validate cross-field/business rules in the service/domain layer where needed.
3. Validate model feature schema and reject missing/extra features according to a documented policy.
4. Run the model pipeline.
5. Validate that outputs are finite and within documented constraints where such constraints are meaningful.
6. Return a typed response with prediction, units, timestamp, model version, and data-quality status.
7. Use consistent error response structures and appropriate HTTP status codes.
8. Log request ID, endpoint, latency, model version, status, and safe metadata. Avoid logging sensitive raw consumption records or secrets.

Suggested endpoints:
- GET /health/live — process is alive.
- GET /health/ready — application and required model artifacts are ready.
- GET /api/v1/models — available model names and versions, without exposing private filesystem details.
- POST /api/v1/residential/predict
- POST /api/v1/commercial/predict
- POST /api/v1/government/predict

FastAPI should be the sole serving interface for inference. Streamlit must call the API through a shared API client; it must not load .pkl files or duplicate prediction logic.

Use dependency injection for model services and settings. Load models once during application startup/lifespan, validate them, and manage readiness if a model fails to load. For a small initial app, a local file-based data source is acceptable, but use clear interfaces so storage can change later.

12. PYTEST STRATEGY
====================================================================

Use pytest throughout. Tests should be fast, deterministic, isolated, and independent of production data/services.

UNIT TESTS
- Pydantic valid/invalid request and response schemas.
- Missing columns, unexpected columns, invalid types, NaN/inf, invalid ranges, timestamp errors.
- Data quality checks, duplicate handling, missing intervals, and zero-value policy.
- Feature engineering and aggregation correctness.
- Billing calculation and tariff configuration.
- Model loader behaviour for missing, corrupt, incompatible, or wrong-type artifacts.
- Model adapter input shape, feature ordering, and output validation.
- Evaluation metric calculations and edge cases.
- Service-layer orchestration and exception handling.

API TESTS
- Health and readiness endpoint behaviour.
- Each prediction endpoint with valid input.
- Each endpoint with invalid/missing inputs.
- Model unavailable, inference error, and malformed output scenarios.
- Response schema and status codes.
- Use FastAPI TestClient and dependency overrides/mocked models so API tests do not depend on large real artifacts.

INTEGRATION TESTS
- A small synthetic data file flows through ingestion, validation, Bronze/Silver/Gold transformations, and report generation.
- API request -> service -> model adapter -> validated response.
- Streamlit API client handles valid responses, timeouts, HTTP errors, and invalid JSON/schema.
- Prediction snapshots, if persistence is included.

CONTRACT TESTS
- Model input columns match the artifact's declared feature schema.
- Pipeline accepts representative raw inputs and returns the expected output shape.
- API schemas remain consistent with the Streamlit client.
- Artifact metadata matches actual model metadata.

RELEASE/SMOKE TESTS
- All three configured artifacts exist and load.
- One known-good sample input can be predicted by each model.
- Outputs are finite and match expected schema/units.
- Model metadata/checksum can be verified.
- Health/readiness checks pass.
- A local end-to-end smoke test can call each endpoint.

Use synthetic or anonymised fixtures; never require confidential production data for ordinary unit tests. Mark slower integration/release tests separately, for example with pytest markers.

13. QUALITY GATES AND RELEASE TESTING
====================================================================

Run gates locally and in CI before merge/release. Suggested sequence:

Gate 1 — Repository hygiene
- Formatting: Ruff formatter or Black.
- Linting: Ruff.
- Type checking: mypy or pyright for critical modules.
- No committed secrets or environment files.
- Dependency/security checks as appropriate.

Gate 2 — Data quality
- Dataset schema matches its declared contract.
- Required columns and types exist.
- Data-quality report generated.
- Configured critical rules pass; warnings are surfaced.
- Row-count changes and data drift are reviewed rather than silently accepted.

Gate 3 — Model quality
- Artifacts load in the target environment.
- Feature schema and dependency versions match.
- Evaluation report exists for every model.
- Held-out metrics and baseline comparisons are available.
- Leakage checks and time-based split checks pass for time-series models.
- No arbitrary claim of success without measured results.

Gate 4 — Automated tests
- Unit tests pass.
- API tests pass.
- Integration/contract tests pass as required for the release.
- Coverage is reported; define a practical threshold after baseline coverage is measured.
- Critical business rules must have direct tests even if overall coverage is high.

Gate 5 — API/UI smoke test
- FastAPI starts.
- Readiness reports the expected models.
- All three prediction endpoints return schema-valid responses on sample inputs.
- Streamlit starts and can reach the API.
- Error states work when the API is unavailable.
- No fake/demo values are mistaken for live predictions.

Gate 6 — Release validation
- Artifact checksums and metadata verified.
- Model/data/code versions recorded.
- Release notes and known limitations written.
- Configuration and secrets supplied via the target environment.
- Rollback path to the last known-good artifacts/code is documented.
- Run a post-release health and prediction smoke test.

A release should be blocked by critical schema failures, missing artifacts, failing tests, invalid model outputs, missing required evaluation reports, or unexplained degradation against the agreed baseline.
